# ADR 0008 — 任务状态机扩展与删除按钮改造

**状态**：已确认
**日期**：2026-06-23
**关联模块**：7月迭代 模块二（调度引擎与任务中心）

## 背景

清单模块二要求"调度台及任务列表所有'删除任务'变更为'终止任务'。终止后置为 inactive，不可物理删除，强制保留记录供后续安全追溯"。

现状：
- 任务状态枚举仅六态：待执行/执行中/已完成/已暂停/已取消/失败
- 调度台已在用 `auto_pending` 字面量表示"冲突待人工处理"，但未进正式枚举
- 删除任务为物理删除（MockService 直接 filter 移除）
- 取消任务已有原因弹窗 + 调度台记录留痕雏形

## 决策

任务状态机扩展为 **8 态**：

| 状态 | 语义 | 流转 |
|---|---|---|
| 待执行 | 已创建未开始 | 现有 |
| 执行中 | 正在跑 | 现有 |
| 已完成 | 正常跑完 | 现有 |
| 已暂停 | 被抢占挂起，可自动恢复 | 现有 |
| **待处理** | 资源冲突待人工裁决，必须操作员介入才流转 | **新增**（正式化现状 `auto_pending`） |
| 已取消 | 未执行即撤销，无执行记录 | 现有，语义收窄 |
| **已终止** | 执行中强制终止，带审计留痕，不可物理删除 | **新增** |
| 失败 | 执行出错 | 现有 |

**边界区分**：
- 已暂停 = 自动可恢复（等高优任务跑完自动恢复）
- 待处理 = 必须人工介入才流转（操作员裁决后流转）
- 两者独立状态，不合并

**删除按钮改造**：移除"删除任务"按钮，只留"终止任务"按钮。不可物理删除，强制保留记录供审计追溯。

## 理由

- 已暂停和待处理的流转路径不同——前者自动恢复，后者必须人工介入，合并会让状态机流转逻辑混乱
- 删除按钮保留会违背清单"不可物理删除强制保留记录"的意图，mock 阶段物理删除会丢审计数据
- `auto_pending` 已在 UI 落地，正式化为枚举状态是顺势收口

## 后果

- 状态枚举新增"待处理"和"已终止"两态
- 调度台 `auto_pending` 字面量替换为正式枚举值
- 删除任务接口（`deleteTask`）废弃，所有调用点改为终止任务接口
- **现状 `terminateTask` 函数保留并对接新"已终止"状态**（现状已有此函数，复用并补充审计日志写入）
- 终止任务接口置状态为"已终止"，保留记录，写入 localStorage audit-log（模块一操作审计日志页面不在本次迭代，见 ADR 0023）
- 任务列表/调度台筛选器需支持新状态筛选
- 报表统计需区分"已取消"和"已终止"
