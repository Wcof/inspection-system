# premortem — 风险分析

日期：2026-07-01
场景：假设算法管理页已上线运行 3 个月，现在复盘发现它失败了。为什么会失败？

---

## Tigers（高危险·低难度 — 必须先处理）

### T1 · 检测规则 algorithm 字段仍是自由字符串，算法管理页成"孤岛"
- **危险**：算法管理页建了一堆算法实体，但检测规则配置时 `algorithm` 字段还是手填字符串（`model.ts` L11），用户根本不进算法管理页，新页面沦为死页面，PM 复盘判定"做了没人用"
- **难度**：低（只需在检测规则表单把 algorithm 输入框改为下拉，数据源从 `getAlgorithms()` 取）
- **缓解**：**但此改造在 Out of Scope（A18/Q7）**。折中方案：算法管理页列表行加"引用情况"列（展示被多少检测规则引用，扫描 `detection_item_configs` 的 algorithm 字段统计），让管理员能看到算法的实际使用情况，避免孤岛感。引用统计是只读展示，不改检测规则表单，零回归
- **触发条件**：算法管理页上线后 30 天内无任何检测规则的 algorithm 字段值与算法管理中的算法名匹配

### T2 · "上传的算法"字段过简，用户不知道配什么
- **危险**：种子只说"上传算法"，若只配个名称，用户会问"模型文件呢？版本呢？适用场景呢？"，3 个月后复盘发现字段不够用反复加字段
- **难度**：低（表单加字段而已）
- **缓解**：按推荐默认 Q2 一次配齐：名称+类型+版本(选填)+模型文件(mock 文件名+大小)+描述+启用状态。原型阶段模型文件走 mock，但字段位都留好

### T3 · user prompt 是纯文本，用户写成"识别一下"这种废话 prompt
- **危险**：大模型的 user prompt 没有结构化引导，用户随便写一句，识别效果差，复盘归因"算法管理页没用"
- **难度**：低（表单加 placeholder + 示例提示）
- **缓解**：user prompt 输入框加 placeholder（如"请识别图中目标，输出 JSON：{result, confidence}"）+ 下方灰色提示"建议明确识别目标、输出格式、判定标准"。预置 2 条大模型自带规范 prompt 作样板（Q3）

---

## Paper Tigers（看起来危险·实际低危 — 别过度投入）

### PT1 · 删除算法导致检测规则悬空引用
- **看起来危险**：硬删算法后，检测规则的 `algorithm` 字段变成悬空字符串
- **实际低危**：原型阶段数据量小，且按 Q6 推荐做软校验提示（弹 Modal 显示被 N 条引用），用户确认才删。即使悬空，检测规则表单回填时 algorithm 是字符串不会报错，最多显示一个不存在的算法名
- **不过度投入**：不做软删除/删除日志/引用级联清理。软校验提示足够

### PT2 · 算法名称重复导致引用歧义
- **看起来危险**：两个算法同名，检测规则引用时不知道指哪个
- **实际低危**：Q1 推荐全局唯一校验，保存时查重拦截即可。原型阶段无并发写入
- **不过度投入**：不做名称相似度检测/同义词合并，简单精确匹配查重

---

## Elephants（高危险·高难度 — 需 PM 决策是否做）

### E1 · 算法管理页与检测规则"大模型增强"开关的关系
- **危险**：算法管理页建了"大模型"实体，但检测规则的 `llmEnabled` 开关仍是裸开关，不指定用哪个大模型兜底。3 个月后 PM 复盘："建了大模型实体但规则兜底还是不知道调哪个，白建了"
- **难度**：中（需改检测规则表单，加"兜底大模型"下拉，关联改造跨 2 个页面）
- **决策**：**本期不做（Out of Scope A12/Q7）**。理由：种子明确"主要就是算法的CRUD"，关联改造会扩大范围。但算法管理页的"大模型"实体建模时字段要对齐未来兜底场景（user prompt 字段就是为兜底调用准备的），确保未来打通时无需重构算法实体
- **风险残留**：若 PM 后续不安排打通，算法管理页的大模型实体可能闲置。需在 PRD 验收标准中明确"本期不验证大模型被实际调用，只验证 CRUD 闭环"

### E2 · "上传的算法"未来要真实上传模型文件
- **危险**：原型用 mock 文件名，未来接真实模型文件上传时，数据结构（文件名+大小）不够用，需要改 Algorithm 类型加 fileUrl/fileHash/fileType 等
- **难度**：中（数据结构迁移 + 上传服务对接）
- **决策**：**本期不做真实上传**。Algorithm 类型设计时预留 `file?: { name, size, type? }` 字段，未来扩展为 `{ name, size, type, url, hash }` 不破坏现有结构
- **风险残留**：未来真实上传需补字段迁移，但向后兼容

---

## 风险摘要

| 类别 | 数量 | 处理策略 |
|------|------|----------|
| Tigers | 3 | T1 引用统计列（零改动的折中）+ T2/T3 字段一次配齐+prompt 引导 |
| Paper Tigers | 2 | 软校验提示 + 查重拦截，不过度投入 |
| Elephants | 2 | 本期不做，类型设计预留扩展位，PRD 明确验收边界 |

## 最关键的一条
**T1**：算法管理页最大的失败风险是"建了没人用"。用"引用统计列"零回归折中缓解，根因解决（检测规则 algorithm 改下拉）留待 PM 后续安排。
